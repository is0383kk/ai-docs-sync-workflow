Workboard Plugin, [Control UI](/hi/web/control-ui) में एक वैकल्पिक Kanban-शैली बोर्ड जोड़ता है: एजेंट के अनुरूप आकार वाले कार्य कार्ड, एजेंटों को असाइनमेंट, और कार्ड के टास्क, रन तथा डैशबोर्ड सेशन पर वापस जाने के लिए एक लिंक।

Workboard को जानबूझकर छोटा रखा गया है: यह एक OpenClaw Gateway के लिए स्थानीय परिचालन कार्य को ट्रैक करता है। यह GitHub Issues, Linear, Jira या अन्य टीम परियोजना प्रबंधन प्रणालियों का विकल्प नहीं है।

## इसे सक्षम करें

Workboard बंडल में शामिल है, लेकिन डिफ़ॉल्ट रूप से अक्षम है:

1. Control UI में **Plugins** खोलें, या कॉन्फ़िगर किए गए Control UI बेस पाथ के सापेक्ष `/settings/plugins` का उपयोग करें। उदाहरण के लिए, `/openclaw` बेस पाथ के लिए `/openclaw/settings/plugins` का उपयोग होता है।
2. **Workboard** खोजें और **Enable** चुनें। चूँकि Workboard, OpenClaw के साथ शामिल है, इसलिए इसके लिए **Install** कार्रवाई की आवश्यकता नहीं है।
3. यदि UI सूचित करता है कि पुनः आरंभ करना आवश्यक है, तो Gateway को पुनः आरंभ करें।

Plugin रनटाइम लोड होने के बाद Workboard टैब डैशबोर्ड नेविगेशन में दिखाई देता है। इसके अक्षम रहने पर टैब नेविगेशन से छिपा रहता है। Plugin अक्षम होने या `plugins.allow`/`plugins.deny` द्वारा अवरुद्ध होने पर सीधे `/workboard` रूट खोलने से कार्ड डेटा के बजाय Plugin-अनुपलब्ध स्थिति दिखाई देती है।

समतुल्य CLI कार्यप्रवाह यह है:

```bash
openclaw plugins enable workboard
openclaw gateway restart
openclaw dashboard
```

## कॉन्फ़िगरेशन

Workboard का कोई Plugin-विशिष्ट कॉन्फ़िगरेशन नहीं है। इसे मानक Plugin प्रविष्टि से सक्षम/अक्षम करें:

```json5
{
  plugins: {
    entries: {
      workboard: {
        enabled: true,
        config: {},
      },
    },
  },
}
```

```bash
openclaw plugins disable workboard
openclaw gateway restart
```

## कार्ड फ़ील्ड

| फ़ील्ड       | मान                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------- |
| `status`    | `triage`, `backlog`, `todo`, `scheduled`, `ready`, `running`, `review`, `blocked`, `done`                     |
| `priority`  | `low`, `normal`, `high`, `urgent`                                                                             |
| `labels`    | मुक्त-रूप स्ट्रिंग                                                                                             |
| `agentId`   | वैकल्पिक रूप से असाइन किया गया एजेंट                                                                                       |
| लिंक किए गए संदर्भ | वैकल्पिक टास्क, रन, सेशन या स्रोत URL                                                                    |
| `execution` | कार्ड से प्रारंभ किए गए Codex/Claude रन के लिए वैकल्पिक मेटाडेटा (इंजन, मोड, मॉडल, सेशन, रन आईडी, स्थिति) |

कार्ड में प्रयासों, टिप्पणियों, लिंकों, प्रमाण, आर्टिफ़ैक्ट, ऑटोमेशन सेटिंग, अटैचमेंट, वर्कर लॉग, वर्कर प्रोटोकॉल स्थिति, दावों, डायग्नोस्टिक्स, सूचनाओं, टेम्पलेट आईडी, संग्रह स्थिति और पुराने सेशन की पहचान के लिए संक्षिप्त मेटाडेटा के साथ हाल की घटनाओं की सूची (`created`, `edited`, `moved`, `linked`, `specified`, `decomposed`, `claimed`, `heartbeat`, `execution_updated`, `attempt_started`, `attempt_updated`, `comment_added`, `link_added`, `proof_added`, `artifact_added`, `attachment_added`, `diagnostic`, `notification`, `dispatch`, `orchestration`, `protocol_violation`, `archived`, `unarchived`, `stale`) भी होती है। यह मेटाडेटा किसी ऑपरेटर को लिंक किया गया सेशन खोले बिना यह देखने देता है कि कार्ड बोर्ड में कैसे आगे बढ़ा; यह स्थानीय परिचालन संदर्भ है, सेशन ट्रांसक्रिप्ट या GitHub इश्यू इतिहास का विकल्प नहीं।

Plugin और Control UI एक ही Workboard कार्ड अनुबंध का उपयोग करते हैं। इसलिए डैशबोर्ड रीफ़्रेश, कार्ड की केवल UI वाली छोटी प्रति प्रस्तुत करने के बजाय वर्कस्पेस उद्गम और प्राधिकार, दावे की स्थिति, डायग्नोस्टिक कार्रवाइयाँ तथा सूचना क्रमांक सुरक्षित रखते हैं। अज्ञात डायग्नोस्टिक प्रकारों, डायग्नोस्टिक गंभीरताओं और सूचना प्रकारों को तब तक अनदेखा किया जाता है, जब तक दोनों सतहें उनका समर्थन न करें; उन्हें कभी किसी अन्य मान्य स्थिति में पुनर्लिखित नहीं किया जाता।

खुला डैशबोर्ड `plugin.workboard.changed` अमान्यकरणों से अपडेट होता है। प्रत्येक घटना में केवल स्टोर युग और संशोधन होता है; इसके बाद UI सामान्य `operator.read` RPC के माध्यम से प्रामाणिक कार्डों को फिर से पढ़ता है। एकाधिक संशोधन एक अनुवर्ती रीड में संयोजित हो जाते हैं। कार्ड को खींचे, संपादित या लिखे जाते समय Workboard उस रीड को स्थगित करता है और स्थानीय इंटरैक्शन पूरा होने के बाद फिर से शुरू करता है। पुनः कनेक्शन हमेशा प्रामाणिक रीलोड करता है। नियमित रूप से पूरे कार्ड का पोल नहीं किया जाता और मैन्युअल पुनर्प्राप्ति के लिए **Refresh** उपलब्ध रहता है।

एक से अधिक बोर्ड होने पर टूलबार में **Board** फ़िल्टर शामिल होता है, जो केवल वर्तमान में दिखाई दे रहे कार्डों के बजाय सहेजे गए बोर्ड मेटाडेटा पर आधारित होता है। इसलिए खाली और संग्रहित बोर्ड भी चयन योग्य रहते हैं। स्पष्ट बोर्ड आईडी के बिना कार्ड प्रामाणिक `default` बोर्ड के अंतर्गत आते हैं। प्रत्येक बोर्ड का एक प्रामाणिक `/workboard/<boardId>` पृष्ठ होता है, जिसे बुकमार्क, साझा या साइडबार में पिन किया जा सकता है। पहले जारी किया गया `/workboard?board=<boardId>` रूप संगतता उपनाम के रूप में बना रहता है और अन्य क्वेरी पैरामीटर सुरक्षित रखते हुए उस पृष्ठ पर रीडायरेक्ट करता है। **All boards** चुनने पर `/workboard` पर वापसी होती है।

कार्ड Plugin की अपनी Gateway स्थिति में संग्रहीत होते हैं और उस Gateway की शेष OpenClaw स्थिति के साथ स्थानांतरित होते हैं ([स्टोरेज](#storage) देखें)।

## कार्ड से काम शुरू करना

लिंक न किए गए कार्ड सीधे काम शुरू कर सकते हैं:

- **Run Codex** / **Run Claude** स्पष्ट इंजन के साथ टास्क-ट्रैक किया गया एजेंट रन शुरू करता है, कार्ड प्रॉम्प्ट भेजता है और कार्ड को `running` चिह्नित करता है। Codex रन `openai/gpt-5.6-sol` का उपयोग करते हैं; Claude रन `anthropic/claude-sonnet-4-6` का उपयोग करते हैं।
- **Open Codex** / **Open Claude** कार्ड प्रॉम्प्ट भेजे या कार्ड को स्थानांतरित किए बिना एक लिंक किया गया डैशबोर्ड सेशन बनाता है, ताकि मैन्युअल कार्य बोर्ड से जुड़ा रहे।

स्वायत्त प्रारंभ Gateway के टास्क-ट्रैक किए गए एजेंट रन पाथ का उपयोग करते हैं (जब तक Codex/Claude स्पष्ट रूप से न चुना जाए, डिफ़ॉल्ट एजेंट और मॉडल); इसके बाद Workboard परिणामी टास्क, रन आईडी और सेशन कुंजी को वापस कार्ड से लिंक करता है। प्रत्येक लिंक किया गया निष्पादन प्रयास का सारांश (इंजन, मोड, मॉडल, रन आईडी, टाइमस्टैम्प, स्थिति, क्रमिक विफलता संख्या) भी दर्ज करता है, ताकि बार-बार होने वाली विफलताएँ दिखाई देती रहें।

डैशबोर्ड Gateway टास्क लेजर से टास्क की स्थिति रीफ़्रेश करता है और टास्क आईडी, रन आईडी या लिंक की गई सेशन कुंजी के आधार पर टास्क को कार्ड से मिलाता है। कतारबद्ध/चल रहा टास्क कार्ड के जीवनचक्र को सक्रिय रखता है; पूर्ण, विफल, समय-सीमा पार या रद्द किया गया टास्क, लिंक किए गए सेशन के समान सिंक नियम का उपयोग करके कार्ड को `review` या `blocked` की ओर ले जाता है ([सेशन जीवनचक्र सिंक](#session-lifecycle-sync) देखें)।

| `workboard_move`                                                                                                                                 | कार्ड को दूसरी स्थिति में ले जाएँ; क्लेम किए गए कार्ड के लिए कॉलर का एजेंट क्लेम स्कोप आवश्यक है।                                                                                                      |
| `workboard_dispatch`                                                                                                                             | वर्कर लॉन्च किए बिना निर्भरता प्रोमोशन या स्टेल-क्लेम सफ़ाई को प्रेरित करें; वर्कर लॉन्च Gateway या स्लैश-कमांड डिस्पैच का उपयोग करता है।                                                        |

प्रमाण स्थितियाँ वर्कर द्वारा रिपोर्ट किए गए परिणाम हैं, स्वतंत्र सत्यापन नहीं। एक `passed`
प्रविष्टि का अर्थ है कि वर्कर रिपोर्ट करता है कि उसका कमांड या जाँच सफल रही; जिन उपभोक्ताओं को
स्वतंत्र गुणवत्ता गेट की आवश्यकता है, उन्हें संलग्न कमांड, URL या आर्टिफ़ैक्ट का निरीक्षण करके
अपना सत्यापक चलाना चाहिए। `workboard_proof` नए रिकॉर्ड का `proofId` लौटाता है। जब
`workboard_complete` उसी प्रमाण की टर्मिनल स्थिति रिपोर्ट करे, तो `proofId` पास करें, ताकि
लंबित रिकॉर्ड अपनी पहचान या टाइमस्टैम्प खोए बिना उसी स्थान पर हल हो जाए। जिस प्रमाण की
टर्मिनल स्थिति पहले से समान है, उसे बिना बदलाव के पुनः उपयोग किया जाता है। `proofId`
के बिना पूर्णता प्रमाण केवल जोड़ने योग्य बना रहता है, इसलिए बाद का पुनः प्रयास पुराने इतिहास को केवल
इस कारण दोबारा नहीं लिख सकता कि उसका कमांड या नोट समान है।

क्लेम किए गए कार्ड अन्य एजेंटों के एजेंट-टूल म्यूटेशन अस्वीकार करते हैं, जब तक कि कॉलर के पास
`workboard_claim` द्वारा लौटाया गया क्लेम टोकन न हो। एजेंट टूल या Gateway RPC कॉल द्वारा लौटाया गया
प्रत्येक कार्ड `metadata.claim.token` को `[redacted]` में रेडैक्ट करता है
(टोकन स्वयं केवल `workboard_claim` से एक बार, शीर्ष-स्तर पर लौटाया जाता है),
ताकि डैशबोर्ड ऑपरेटर और अन्य एजेंट कभी उपयोग योग्य टोकन देखे बिना
क्लेम स्थिति का निरीक्षण कर सकें। रिकवरी
`workboard_promote`/`workboard_reassign`/`workboard_reclaim` के माध्यम से होती है, जिनके लिए
टोकन आवश्यक नहीं है।

## डिस्पैच

डिस्पैच Gateway-लोकल है: यह मनमाने OS प्रोसेस शुरू नहीं करता। सामान्य
OpenClaw सबएजेंट सत्र ही निष्पादन के स्वामी बने रहते हैं। एक डिस्पैच पास:

1. निर्भरता के लिए तैयार कार्डों को प्रोमोट करता है।
2. तैयार कार्डों पर डिस्पैच मेटाडेटा रिकॉर्ड करता है।
3. समाप्त हो चुके क्लेम या टाइम-आउट रन को अवरुद्ध करता है।
4. बोर्ड-कॉन्फ़िगर किए गए ट्रायेज कार्डों को ऑर्केस्ट्रेशन उम्मीदवार के रूप में चिह्नित करता है।
5. तैयार कार्डों के एक छोटे बैच को क्लेम करता है और
   Gateway सबएजेंट रनटाइम के माध्यम से वर्कर रन शुरू करता है।

वर्कर को सीमित कार्ड संदर्भ के साथ क्लेम टोकन मिलता है, जिसकी आवश्यकता Workboard टूल के माध्यम से
Heartbeat भेजने, कार्ड पूरा करने या अवरुद्ध करने के लिए होती है।

वर्कस्पेस पथ कॉलर के मौजूदा फ़ाइलसिस्टम प्राधिकार का अनुसरण करते हैं। `operator.write` वाले Gateway
क्लाइंट कॉन्फ़िगर किए गए एजेंट वर्कस्पेस का उपयोग कर सकते हैं;
`operator.admin` क्लाइंट अन्य होस्ट चेकआउट का उपयोग कर सकते हैं। सैंडबॉक्स किए गए एजेंट टूल अपने
सैंडबॉक्स वर्कस्पेस एक्सेस का उपयोग करते हैं, जबकि बिना सैंडबॉक्स वाले केवल-वर्कस्पेस टूल अपने
कॉन्फ़िगर किए गए वर्कस्पेस रूट का उपयोग करते हैं। वर्कस्पेस असाइन किए जाने पर Workboard उस प्राधिकार को
रिकॉर्ड करता है और डिस्पैच के समय उसे वर्तमान कॉलर के प्राधिकार के साथ फिर से इंटरसेक्ट करता है,
इसलिए कोई स्थायी कार्ड बाद के कॉलर की पहुँच नहीं बढ़ा सकता। स्पष्ट होस्ट वर्कस्पेस वाले लेकिन
रिकॉर्ड किए गए प्राधिकार के बिना पुराने कार्डों के वर्कस्पेस को पूर्ण-होस्ट डिस्पैच से पहले
फिर से सहेजना आवश्यक है; होस्ट पथ के बिना कार्ड पहली बार डिस्पैच होने पर
वर्तमान कॉलर का प्राधिकार अपना लेते हैं।

वर्कस्पेस-बाउंड डिस्पैच किसी डायरेक्टरी या Git चेकआउट को केवल तभी स्वीकार करता है, जब उसका
रिपॉज़िटरी रूट लक्षित एजेंट वर्कस्पेस से बिल्कुल मेल खाता हो। वर्कट्री अनुरोध को
उस डायरेक्टरी तक सीमित किया जाता है और डायरेक्टरी वर्कस्पेस के रूप में स्थायी बनाया जाता है, इसलिए
होस्ट न तो चेकआउट को साकार करता है, न ही रिपॉज़िटरी सेटअप कोड निष्पादित करता है।
लक्षित वर्कर को उसी सटीक वर्कस्पेस के लिए लिखने योग्य, गैर-साझा Docker सैंडबॉक्स का उपयोग करना चाहिए,
जिसमें उन्नत निष्पादन, स्थायी होस्ट/Node exec ओवरराइड या अवर्गीकृत Plugin और MCP टूल न हों।
Workboard किसी `workboard_*` प्रीफ़िक्स पर भरोसा करने के बजाय अपने पंजीकृत टूलों की गणना करता है,
और डिस्पैच ऐसे सक्रिय Docker कंटेनर को अस्वीकार करता है जिसका लाइव माउंट/कॉन्फ़िगरेशन हैश स्टेल हो।
डिस्पैच कम प्रतिबंधित वर्कर शुरू करने के बजाय असंगत लक्ष्य नीति रिपोर्ट करता है।
पूर्ण-होस्ट डिस्पैच अन्य स्थानीय चेकआउट को लक्षित कर सकता है और सामान्य प्रबंधित-
वर्कट्री सेटअप बनाए रखता है।

वर्कस्पेस प्राधिकार कार्ड लाइफ़साइकल के लिए दूसरा अनुमति मॉडल नहीं बनाता।
Workboard कार्डों को म्यूटेट करने की अनुमति रखने वाले कॉलर प्रत्येक सतह पर उन्हें मैन्युअल रूप से
समान स्थितियों के बीच ले जा सकते हैं; केवल-पढ़ने योग्य वर्कस्पेस एक्सेस केवल ऐसे वर्कर
डिस्पैच को रोकता है जिसे लिखने की आवश्यकता होती है।

### वर्कर चयन

प्रत्येक पास डिफ़ॉल्ट रूप से **अधिकतम 3 वर्कर शुरू करता है**। तैयार कार्ड को
पहले प्राथमिकता, फिर स्थिति, फिर निर्माण समय के अनुसार क्रमबद्ध किया जाता है। एक पास प्रत्येक
स्वामी/एजेंट के लिए केवल एक कार्ड शुरू करता है और उन स्वामियों को छोड़ देता है जिनका
बोर्ड पर पहले से कार्य चल रहा है या समीक्षा में है। संग्रहीत कार्ड, सक्रिय क्लेम वाले कार्ड और जो कार्ड `ready`
स्थिति में नहीं हैं, उन्हें वर्कर शुरू करने के लिए कभी नहीं चुना जाता (वे फिर भी
डिस्पैच के डेटा पक्ष से प्रभावित हो सकते हैं: पुराने क्लेम की सफ़ाई, निर्भरता का प्रमोशन, टाइमआउट
की सफ़ाई)।

सत्र कुंजियाँ प्रत्येक बोर्ड/कार्ड के लिए नियतात्मक होती हैं, इसलिए बार-बार किए गए डिस्पैच
असंबंधित सत्र बनाने के बजाय उसी वर्कर लेन पर वापस भेजे जाते हैं:

- असाइन किए गए कार्ड: `agent:<agentId>:subagent:workboard-<boardId>-<cardId>`
- अनअसाइन किए गए कार्ड: `subagent:workboard-<boardId>-<cardId>` (Gateway
  कॉन्फ़िगर किए गए डिफ़ॉल्ट एजेंट का समाधान करता है)

यदि किसी कार्ड पर क्लेम होने के बाद वर्कर शुरू नहीं किया जा सकता, तो कार्यपट्ट
कार्ड को ब्लॉक करता है, क्लेम हटाता है, रन शुरू करने की विफलता दर्ज करता है और एक वर्कर
लॉग पंक्ति जोड़ता है—जो डैशबोर्ड, CLI JSON, एजेंट टूल और कार्ड
डायग्नोस्टिक्स में दिखाई देती है।

### प्रवेश बिंदु

- डैशबोर्ड डिस्पैच कार्रवाई
- `openclaw workboard dispatch`
- कमांड-सक्षम चैनल पर `/workboard dispatch`

Gateway उपलब्ध होने पर तीनों Gateway सबएजेंट रनटाइम का उपयोग करते हैं।
CLI में एक ऑपरेटर फ़ॉलबैक है: यदि Gateway कॉल
कनेक्शन/अनुपलब्धता त्रुटि (या पुराने
Gateways के लिए `unknown method` त्रुटि) के साथ विफल होती है और कोई स्पष्ट `--url`/`--token` लक्ष्य तथा कोई कॉन्फ़िगर किया गया रिमोट
Gateway (`OPENCLAW_GATEWAY_URL` या `gateway.mode: remote`) लागू नहीं होता, तो CLI स्थानीय SQLite स्थिति पर
केवल-डेटा डिस्पैच चलाता है—यह निर्भरताओं को प्रमोट कर सकता है,
पुराने क्लेम साफ़ कर सकता है और टाइमआउट हुए रन ब्लॉक कर सकता है, लेकिन वर्कर शुरू नहीं कर सकता। पहुँच योग्य Gateway से मिली प्रमाणीकरण,
अनुमति और सत्यापन विफलताओं को
अनुपलब्ध नहीं माना जाता; वे कमांड त्रुटियों के रूप में दिखाई देती हैं, और स्पष्ट `--url`/`--token` लक्ष्य दिए जाने पर कोई भी Gateway
विफलता भी इसी तरह दिखाई देती है।

बोर्ड मेटाडेटा `autoDecompose`, `autoDecomposePerDispatch`,
`defaultAssignee` और `orchestratorProfile` सेट कर सकता है। OpenClaw इस आशय को दर्ज करता है और
इसे वर्कर संदर्भ में उपलब्ध कराता है; वास्तविक विनिर्देशन/विघटन अब भी
सामान्य कार्यपट्ट टूल के माध्यम से चलता है।

## CLI और स्लैश कमांड

```bash
openclaw workboard list [--board <id>] [--status <status>] [--include-archived] [--json]
openclaw workboard create "Fix stale card lifecycle" --priority high --labels bug,workboard
openclaw workboard show <card-id> [--json]
openclaw workboard move <card-id> --status <status> [--json]
openclaw workboard dispatch [--board <id>] [--json]
```

`list` टेक्स्ट आउटपुट डिफ़ॉल्ट रूप से संग्रहीत कार्ड छिपाता है (`--include-archived`
इसे ओवरराइड करता है); `--json` हमेशा संग्रहीत कार्ड शामिल करता है, जो मौजूदा स्क्रिप्ट द्वारा उपयोग किए जाने वाले पूर्ण-कार्ड
कॉन्ट्रैक्ट से मेल खाता है। `show` और `move` एक असंदिग्ध id
उपसर्ग स्वीकार करते हैं। `list`, `create`, `show` और `move` हमेशा स्थानीय Plugin
स्थिति को सीधे पढ़ते/लिखते हैं। केवल `dispatch` चल रहे Gateway को कॉल करता है, जिसमें ऊपर वर्णित
फ़ॉलबैक लागू होता है।

सभी फ़्लैग, JSON आउटपुट, Gateway
फ़ॉलबैक व्यवहार, id-उपसर्ग प्रबंधन, डिस्पैच चयन नियम और
समस्या निवारण के लिए [कार्यपट्ट CLI](/hi/cli/workboard) देखें।

`/workboard list`, `/workboard show <card-id>`, `/workboard create <title>`,
`/workboard move <card-id> --status <status>` और `/workboard dispatch`
CLI के अनुरूप हैं। सूची और प्रदर्शन किसी भी अधिकृत कमांड प्रेषक के लिए पठन कार्रवाइयाँ हैं।
चैट सतहों पर बनाने, स्थानांतरित करने और डिस्पैच करने के लिए स्वामी स्थिति, या `operator.write`/`operator.admin` वाले Gateway
क्लाइंट की आवश्यकता होती है। मैन्युअल ऑपरेटर स्थानांतरण
डैशबोर्ड के ड्रैग-एंड-ड्रॉप जैसा ही क्लेम-ओवरराइड व्यवहार उपयोग करते हैं। उनकी वर्कट्री पहुँच
फिर भी ऊपर वर्णित उसी वर्कस्पेस सीमा का पालन करती है।

## सत्र जीवनचक्र समन्वयन

कार्ड किसी मौजूदा डैशबोर्ड सत्र या कार्ड से कार्य
शुरू करने पर बनाए गए सत्र से लिंक हो सकते हैं। लिंक किए गए कार्ड सत्र जीवनचक्र को इनलाइन दिखाते हैं:
चल रहा, पुराना, लिंक किया गया निष्क्रिय, पूर्ण, विफल या अनुपलब्ध। आप सत्र टैब से **कार्यपट्ट में जोड़ें** का उपयोग करके किसी
मौजूदा सत्र को भी कैप्चर कर सकते हैं; कार्ड
उस सत्र से लिंक होता है, सत्र लेबल या हालिया उपयोगकर्ता प्रॉम्प्ट को शीर्षक के रूप में उपयोग करता है
और उपलब्ध होने पर हालिया उपयोगकर्ता प्रॉम्प्ट तथा नवीनतम सहायक प्रतिक्रिया से
नोट्स आरंभ करता है।

यदि लिंक किया गया सत्र अनुपलब्ध हो जाता है, तो संदर्भ के लिए कार्ड लिंक बना रहता है और
नए सत्र में पुनः आरंभ करने के लिए स्टार्ट नियंत्रण भी उपलब्ध कराता है। यदि कोई सक्रिय
लिंक किया गया सत्र हालिया गतिविधि की रिपोर्ट करना बंद कर देता है, तो कार्यपट्ट कार्ड को
`stale` चिह्नित करता है और जीवनचक्र द्वारा इसे हटाए जाने तक मेटाडेटा के रूप में संग्रहीत करता है।

जब कोई कार्ड सक्रिय कार्य स्थिति में होता है, तो कार्यपट्ट लिंक किए गए सत्र का अनुसरण करता है:

| लिंक किए गए सत्र की स्थिति             | कार्ड की स्थिति |
| ------------------------------------- | ----------- |
| सक्रिय                                | `running`   |
| पूर्ण                                 | `review`    |
| विफल, समाप्त किया गया, टाइमआउट हुआ या निरस्त | `blocked`   |

**मैन्युअल समीक्षा स्थितियों को प्राथमिकता मिलती है।** किसी कार्ड को `review`, `blocked` या `done`
पर ले जाने से उस कार्ड का स्वतः-समन्वयन तब तक रुक जाता है, जब तक आप उसे वापस `todo` या `running` पर नहीं ले जाते।

कार्ड शुरू करने पर सामान्य Gateway सत्र उपयोग होते हैं; कार्यपट्ट केवल कार्ड
मेटाडेटा और लिंक संग्रहीत करता है। वार्तालाप ट्रांसक्रिप्ट, मॉडल चयन और रन
जीवनचक्र का स्वामित्व नियमित सत्र प्रणाली के पास रहता है। सक्रिय
लिंक किए गए कार्ड पर चल रहे रन को निरस्त करने के लिए **रोकें** का उपयोग करें—कार्यपट्ट उस कार्ड को `blocked` चिह्नित करता है, ताकि
वह अनुवर्ती कार्रवाई के लिए दिखाई देता रहे।

नए कार्ड कार्यपट्ट टेम्पलेट (`bugfix`, `docs`, `release`,
`pr_review`, `plugin`) से शुरू हो सकते हैं। टेम्पलेट शीर्षक, नोट्स, लेबल और प्राथमिकता पहले से भरते हैं;
टेम्पलेट id कार्ड मेटाडेटा के रूप में संग्रहीत होता है।

## डैशबोर्ड कार्यप्रवाह

1. नियंत्रण UI में कार्यपट्ट टैब खोलें।
2. शीर्षक, नोट्स, प्राथमिकता, लेबल, वैकल्पिक एजेंट और
   वैकल्पिक लिंक किए गए सत्र के साथ एक कार्ड बनाएँ—या सत्र खोलें और किसी मौजूदा सत्र के लिए **कार्यपट्ट में जोड़ें**
   चुनें।
3. कार्ड को स्तंभों के बीच खींचें, या उसके संक्षिप्त स्थिति नियंत्रण पर फ़ोकस करके
   मेन्यू अथवा ArrowLeft/ArrowRight का उपयोग करें। खींचने के दौरान स्रोत कार्ड धुंधला हो जाता है और
   उपलब्ध ड्रॉप स्तंभों के चारों ओर बाह्यरेखा दिखाई देती है।
4. डैशबोर्ड सत्र बनाने या पुनः उपयोग करने के लिए कार्ड से कार्य शुरू करें।
5. एजेंट के कार्य करते समय कार्ड से लिंक किया गया सत्र खोलें।
6. जीवनचक्र समन्वयन को चल रहे कार्य को `review`/`blocked` में ले जाने दें, फिर स्वीकार होने पर कार्ड को मैन्युअल रूप से
   `done` में ले जाएँ।

### सत्र-बोर्ड विजेट

कार्यपट्ट सत्र डैशबोर्ड के लिए दो मूल विजेट प्रदान करता है (देखें
[डैशबोर्ड](/hi/web/dashboards))। एजेंट अपने `dashboard` टूल से
`content: { kind: "plugin", pluginKind, props }` का उपयोग करके उन्हें पिन करता है और वे
लाइव डेटा के साथ प्रथम-पक्ष UI के रूप में रेंडर होते हैं—कोई सैंडबॉक्स फ़्रेम या क्षमता अनुदान नहीं:

- `workboard:card`, `props: { cardId }` के साथ, एक कार्ड को उसके स्थिति
  नियंत्रण, प्राथमिकता और असाइन किए गए एजेंट सहित दिखाता है।
- वैकल्पिक `props: { boardId, limit }` के साथ `workboard:mini` प्रत्येक स्थिति की
  संख्या तथा शीर्ष तैयार/चल रहे कार्ड दिखाता है और पूर्ण बोर्ड पृष्ठ से लिंक करता है।
  `boardId` के बिना यह प्रत्येक बोर्ड को एकत्रित करता है; `boardId` के साथ इसका दायरा उस
  बोर्ड तक सीमित रहता है (बिना स्पष्ट बोर्ड id के बनाए गए कार्ड `default` पर रहते हैं)।

## डायग्नोस्टिक्स

डायग्नोस्टिक्स की गणना स्थानीय कार्ड मेटाडेटा से की जाती है। अंतर्निहित जाँचें इन्हें चिह्नित करती हैं:

| प्रकार                       | स्थिति                                                                          |
| --------------------------- | ------------------------------------------------------------------------------ |
| `stranded_ready`            | असाइन किया गया `todo`/`backlog`/`ready` कार्ड 1 घंटे से अधिक समय से अपडेट नहीं हुआ।             |
| `running_without_heartbeat` | `running` कार्ड में 20 मिनट से अधिक समय से कोई क्लेम Heartbeat या निष्पादन अपडेट नहीं है। |
| `blocked_too_long`          | `blocked` कार्ड 24 घंटे से अधिक समय से अपडेट नहीं हुआ।                                   |
| `repeated_failures`         | कार्ड की ट्रैक की गई विफलताओं की संख्या 2 या अधिक हो गई है।                                |
| `missing_proof`             | `done` कार्ड में कोई प्रमाण, आर्टिफ़ैक्ट या अटैचमेंट नहीं है।                          |
| `orphaned_session`          | `running` कार्ड में `sessionKey` है, लेकिन कोई `execution` मेटाडेटा नहीं है।                |

## अनुमतियाँ

Gateway RPC विधियाँ `workboard.*` के अंतर्गत रहती हैं:

| दायरा           | विधियाँ                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `operator.read`  | `cards.list`, `cards.export`, `cards.diagnostics`, अटैचमेंट सूची/प्राप्ति, सूचना इवेंट पठन, `boards.list`, `cards.stats`, `cards.runs`                                                                                                                                                                                                                                       |
| `operator.write` | `cards.diagnostics.refresh`, बनाएँ/अपडेट करें/स्थानांतरित करें/हटाएँ/टिप्पणी करें/लिंक करें/linkDependency/प्रमाण/आर्टिफ़ैक्ट, अटैचमेंट जोड़ें/हटाएँ, वर्कर लॉग, प्रोटोकॉल उल्लंघन, क्लेम/Heartbeat/रिलीज़/प्रमोट/पुनः असाइन/पुनः क्लेम/पूर्ण/ब्लॉक/अनब्लॉक, `cards.dispatch`, `cards.bulk`, संग्रहित करें, `boards.upsert`/`archive`/`delete`, `cards.specify`/`decompose`, सूचना सदस्यता लें/हटाएँ/आगे बढ़ाएँ |

किसी RPC विधि को `operator.admin` की आवश्यकता नहीं है। केवल-पठन
ऑपरेटर पहुँच से जुड़े ब्राउज़र बोर्ड का निरीक्षण कर सकते हैं, लेकिन कार्ड में बदलाव नहीं कर सकते। एडमिन दायरा
स्वीकृत कार्यपट्ट होस्ट पथों को विस्तृत करता है; यह उपलब्ध विधियों को नहीं बदलता।

## संग्रहण

कार्यपट्ट स्थायी डेटा को OpenClaw स्थिति डायरेक्टरी के अंतर्गत Plugin के स्वामित्व वाले रिलेशनल SQLite डेटाबेस में
संग्रहीत करता है: बोर्ड, कार्ड, लेबल, जीवनचक्र इवेंट,
रन प्रयास, टिप्पणियाँ, निर्भरता लिंक, प्रमाण, आर्टिफ़ैक्ट संदर्भ,
अटैचमेंट मेटाडेटा और ब्लॉब, डायग्नोस्टिक्स, सूचनाएँ, वर्कर लॉग,
प्रोटोकॉल स्थिति और सदस्यताएँ—सभी कार्यपट्ट तालिकाओं में रहते हैं (Plugin
की-वैल्यू प्रविष्टियों में नहीं)। कार्ड निर्यात अटैचमेंट ब्लॉब की सामग्री इनलाइन किए बिना
बोर्ड की विवरणात्मक कथा सुरक्षित रखता है।

`.28` रिलीज़ में कार्यपट्ट का उपयोग करने वाले इंस्टॉलेशन
रिलीज़ किए गए पुराने Plugin-स्थिति नेमस्पेस
(`workboard.cards`, `workboard.boards`, `workboard.notify` और, यदि मौजूद हो,
`workboard.attachments`) को रिलेशनल डेटाबेस में माइग्रेट करने के लिए `openclaw doctor --fix` चला सकते हैं।

## समस्या निवारण

**टैब बताता है कि कार्यपट्ट उपलब्ध नहीं है**

```bash
openclaw plugins inspect workboard --runtime --json
```

यदि `plugins.allow` कॉन्फ़िगर किया गया है, तो उसमें `workboard` जोड़ें। यदि `plugins.deny`
में `workboard` है, तो Plugin सक्षम करने से पहले उसे हटाएँ।

**कार्ड सहेजे नहीं जाते**

पुष्टि करें कि ब्राउज़र कनेक्शन के पास `operator.write` पहुँच है। केवल-पठन ऑपरेटर
सत्र कार्ड सूचीबद्ध कर सकते हैं, लेकिन उन्हें बना, संपादित, स्थानांतरित या हटा नहीं सकते।

**कार्ड शुरू करने पर अपेक्षित सत्र नहीं खुलता**

कार्ड का एजेंट id और लिंक किया गया सत्र जाँचें, फिर वास्तविक रन स्थिति का
निरीक्षण करने के लिए सत्र या चैट खोलें।

**डिस्पैच वर्कर शुरू नहीं करता**

पुष्टि करें कि सक्रिय क्लेम के बिना कम-से-कम एक `ready` कार्ड मौजूद है:

```bash
openclaw workboard list --status ready
```

यदि CLI केवल-डेटा डिस्पैच की सूचना देता है, तो Gateway को शुरू या पुनः शुरू करें और
दोबारा प्रयास करें—केवल-डेटा डिस्पैच स्थानीय बोर्ड की स्थिति को अपडेट करता है, लेकिन
सबएजेंट वर्कर रन शुरू नहीं कर सकता। कार्ड तब भी छोड़े जा सकते हैं, जब उसी
स्वामी या एजेंट का कोई अन्य कार्ड पहले से चल रहा हो या समीक्षा की प्रतीक्षा में हो; उसी
स्वामी के लिए और कार्ड डिस्पैच करने से पहले उस सक्रिय कार्य को पूरा करें,
ब्लॉक करें या रिलीज़ करें।
