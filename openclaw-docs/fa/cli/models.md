# `openclaw models`

کشف، اسکن و پیکربندی مدل (مدل پیش‌فرض، جایگزین‌ها و پروفایل‌های احراز هویت).

مرتبط:

- ارائه‌دهندگان + مدل‌ها: [مدل‌ها](/fa/providers/models)
- مفاهیم انتخاب مدل + دستور اسلش `/models`: [مفهوم مدل‌ها](/fa/concepts/models)
- راه‌اندازی احراز هویت ارائه‌دهنده: [شروع به کار](/fa/start/getting-started)

## دستورهای رایج

```bash
openclaw models status
openclaw models list
openclaw models set <model-or-alias>
openclaw models set-image <model-or-alias>
openclaw models scan
```

زیردستورهای `status` و `auth` برای هدف‌گیری یک عامل پیکربندی‌شده، `--agent <id>` را می‌پذیرند؛ `list`، `scan`، `aliases` و `fallbacks`/`image-fallbacks` همیشه از عامل پیش‌فرض پیکربندی‌شده استفاده می‌کنند و `set`/`set-image`، `--agent` را به‌طور کامل رد می‌کنند. در صورت حذف، دستورهای آگاه از `--agent`، اگر `OPENCLAW_AGENT_DIR` تنظیم شده باشد از آن استفاده می‌کنند؛ در غیر این صورت از عامل پیش‌فرض پیکربندی‌شده استفاده می‌شود.

### وضعیت

`openclaw models status` مدل پیش‌فرض و جایگزین‌های نهایی را به‌همراه نمایی کلی از احراز هویت نشان می‌دهد. برای زمان‌های اجرای عامل که در مالکیت Plugin هستند، مانند Codex، همچنین بررسی می‌کند که آیا Plugin مالک فعال است و تأیید بار راه‌اندازی را گذرانده است یا نه. مسیری با اعتبارنامه‌های معتبر اما زمان اجرای دردسترس‌نبودنی، به‌جای `usable`، `status: unavailable` را گزارش می‌کند؛ خروجی JSON شامل `authStatus`، `runtimeStatus` و عیب‌یابی محدود زمان اجرا به‌صورت جداگانه است. هنگامی که نماهای لحظه‌ای استفاده از ارائه‌دهنده موجود باشند، بخش وضعیت OAuth/کلید API شامل بازه‌های استفاده از ارائه‌دهنده و نماهای لحظه‌ای سهمیه است. ارائه‌دهندگان فعلی بازه استفاده: Anthropic، GitHub Copilot، Gemini CLI، OpenAI، MiniMax، Xiaomi و z.ai. احراز هویت استفاده، در صورت وجود، از هوک‌های ویژه ارائه‌دهنده دریافت می‌شود؛ در غیر این صورت OpenClaw به اعتبارنامه‌های منطبق OAuth/کلید API از پروفایل‌های احراز هویت، محیط یا پیکربندی بازمی‌گردد.

در خروجی `--json`، `auth.providers` نمای کلی ارائه‌دهنده با آگاهی از محیط/پیکربندی/ذخیره‌گاه است، درحالی‌که `auth.oauth` فقط سلامت پروفایل در ذخیره‌گاه احراز هویت را نشان می‌دهد.

گزینه‌ها:

| پرچم                      | اثر                                                                                                                                   |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `--json`                  | خروجی JSON؛ عیب‌یابی پروفایل احراز هویت، ارائه‌دهنده و راه‌اندازی به stderr می‌رود تا stdout برای انتقال به `jq` قابل استفاده بماند.                            |
| `--plain`                 | خروجی متن ساده.                                                                                                                       |
| `--check`                 | اگر احراز هویت در آستانه انقضا/منقضی باشد یا زمان اجرای عامل انتخاب‌شده دردسترس نباشد، با کد غیرصفر خارج می‌شود: `1` = دردسترس‌نبودن/انقضا/فقدان، `2` = در آستانه انقضا. |
| `--probe`                 | کاوش زنده پروفایل‌های احراز هویت پیکربندی‌شده. درخواست‌های واقعی؛ ممکن است توکن مصرف کند و محدودیت نرخ را فعال کند.                                       |
| `--probe-provider <name>` | فقط یک ارائه‌دهنده را کاوش می‌کند.                                                                                                                 |
| `--probe-profile <id>`    | شناسه‌های پروفایل احراز هویت مشخص را کاوش می‌کند (تکرارشونده یا جداشده با ویرگول).                                                                             |
| `--probe-timeout <ms>`    | مهلت زمانی هر کاوش.                                                                                                                       |
| `--probe-concurrency <n>` | کاوش‌های هم‌زمان.                                                                                                                       |
| `--probe-max-tokens <n>`  | حداکثر توکن‌های کاوش (در حد توان).                                                                                                          |
| `--agent <id>`            | شناسه عامل پیکربندی‌شده؛ `OPENCLAW_AGENT_DIR` را لغو می‌کند.                                                                                     |

ردیف‌های کاوش ممکن است از پروفایل‌های احراز هویت، اعتبارنامه‌های محیط یا `models.json` بیایند. دسته‌های وضعیت کاوش: `ok`، `auth`، `rate_limit`، `billing`، `timeout`، `format`، `unknown`، `no_model`.

کدهای جزئیات/دلیل مورد انتظار هنگامی که یک کاوش هرگز به فراخوانی مدل نمی‌رسد:

- `excluded_by_auth_order`: یک پروفایل ذخیره‌شده وجود دارد، اما `auth.order.<provider>` صریح آن را حذف کرده است؛ بنابراین کاوش به‌جای امتحان‌کردن آن، حذف را گزارش می‌کند.
- `missing_credential`، `invalid_expires`، `expired`، `unresolved_ref`: پروفایل موجود است، اما واجد شرایط یا قابل تفکیک نیست.
- `ineligible_profile`: پروفایل به دلیل دیگری با پیکربندی ارائه‌دهنده ناسازگار است.
- `no_model`: احراز هویت ارائه‌دهنده وجود دارد، اما OpenClaw نتوانسته است یک نامزد مدل قابل کاوش برای آن ارائه‌دهنده تفکیک کند.

برای عیب‌یابی OAuth مربوط به OpenAI ChatGPT/Codex، سریع‌ترین راه تأیید اینکه آیا یک عامل پروفایل OAuth قابل استفاده `openai` برای `openai/*` از طریق زمان اجرای بومی Codex دارد، استفاده از `openclaw models status`، `openclaw models auth list --provider openai` و `openclaw config get agents.defaults.model --json` است. [راه‌اندازی ارائه‌دهنده OpenAI](/fa/providers/openai#check-and-recover-codex-oauth-routing) را ببینید.

### فهرست

`openclaw models list` فقط‌خواندنی است: پیکربندی، پروفایل‌های احراز هویت، وضعیت موجود کاتالوگ و ردیف‌های کاتالوگ متعلق به ارائه‌دهنده را می‌خواند، اما هرگز `models.json` را بازنویسی نمی‌کند.

گزینه‌ها: `--all` (کاتالوگ کامل)، `--local` (فیلترکردن به مدل‌های محلی)، `--provider <id>`، `--json`، `--plain`.

نکته‌ها:

- ستون `Auth` فقط‌خواندنی است. برای مسیرهای مدل متعلق به ارائه‌دهنده مانند OpenAI، مسیر API/نشانی پایه هر ردیف را با پروفایل‌های واجد شرایط در `auth.order` مؤثر، اعتبارنامه‌های محیط/پیکربندی و SecretRefهای تفکیک‌شده در محدوده دستور تطبیق می‌دهد. هنگامی که سیاست مسیر یک ردیف مشخص OpenAI دردسترس نیست، وضعیت آن ناشناخته باقی می‌ماند و احراز هویت سطح ارائه‌دهنده را قرض نمی‌گیرد؛ بررسی‌های قدیمی فقط ارائه‌دهنده و سایر ارائه‌دهندگان، رفتار سطح ارائه‌دهنده را حفظ می‌کنند. فراداده احراز هویت مصنوعی Plugin فقط نشانه‌ای از قابلیت زمان اجرا است، نه اثبات احراز هویت بومی حساب؛ بنابراین مسیرهای وابسته به حساب بدون شواهد مثبت رجیستری ناشناخته باقی می‌مانند. این دستور زمان اجرای ارائه‌دهنده را بارگیری نمی‌کند، اسرار زنجیره‌کلید را نمی‌خواند، APIهای ارائه‌دهنده را فراخوانی نمی‌کند و آمادگی دقیق اجرا را اثبات نمی‌کند.
- `models list --all --provider <id>` می‌تواند حتی پیش از احراز هویت با آن ارائه‌دهنده، ردیف‌های ثابت کاتالوگ متعلق به ارائه‌دهنده را از مانیفست‌های Plugin یا فراداده کاتالوگ ارائه‌دهنده همراه‌شده شامل شود. تا زمانی که احراز هویت منطبق پیکربندی نشود، این ردیف‌ها همچنان دردسترس‌نبودن را نشان می‌دهند.
- `models list` در هنگام کندبودن کشف کاتالوگ ارائه‌دهنده، صفحه کنترل را پاسخ‌گو نگه می‌دارد. نماهای پیش‌فرض و پیکربندی‌شده پس از انتظاری کوتاه به ردیف‌های مدل پیکربندی‌شده یا مصنوعی بازمی‌گردند و اجازه می‌دهند کشف در پس‌زمینه پایان یابد. وقتی به کاتالوگ کامل و دقیق کشف‌شده نیاز دارید و مایلید منتظر کشف ارائه‌دهنده بمانید، از `--all` استفاده کنید.
- `models list --all` گسترده، بدون بارگیری هوک‌های تکمیلی زمان اجرای ارائه‌دهنده، ردیف‌های کاتالوگ مانیفست را روی ردیف‌های رجیستری ادغام می‌کند. مسیرهای سریع مانیفست فیلترشده براساس ارائه‌دهنده فقط از ارائه‌دهندگانی استفاده می‌کنند که با `static` علامت‌گذاری شده‌اند؛ ارائه‌دهندگان علامت‌گذاری‌شده با `refreshable` متکی به رجیستری/کش باقی می‌مانند و ردیف‌های مانیفست را به‌عنوان مکمل اضافه می‌کنند، درحالی‌که ارائه‌دهندگان علامت‌گذاری‌شده با `runtime` در کشف رجیستری/زمان اجرا باقی می‌مانند.
- `models list` فراداده بومی مدل و سقف‌های زمان اجرا را متمایز نگه می‌دارد. در خروجی جدول، هنگامی که سقف مؤثر زمان اجرا با پنجره زمینه بومی متفاوت باشد، `Ctx`، `contextTokens/contextWindow` را نشان می‌دهد؛ وقتی ارائه‌دهنده چنین سقفی را ارائه کند، ردیف‌های JSON شامل `contextTokens` هستند.
- برای مسیرهای متعلق به ارائه‌دهنده، `models list` یک ردیف منطقی ارائه‌دهنده/مدل را روی مسیر انتخاب‌شده نگاشت می‌کند. `Input` و `Ctx` فقط از ردیف کاتالوگ دقیق مسیر فیزیکی می‌آیند و لغوهای منطقی صریح پیکربندی‌شده در آخر اعمال می‌شوند؛ انتخاب مسیر تفکیک‌نشده، به‌جای قرض‌گرفتن فراداده مسیرهای هم‌خانواده، فیلدهای قابلیت ناشناخته را نشان می‌دهد.
- `models list --provider <id>` براساس شناسه ارائه‌دهنده، مانند `moonshot` یا `openai`، فیلتر می‌کند. برچسب‌های نمایشی انتخابگرهای تعاملی ارائه‌دهنده، مانند `Moonshot AI`، را نمی‌پذیرد.
- ارجاع‌های مدل با تقسیم روی **اولین** `/` تجزیه می‌شوند. اگر شناسه مدل شامل `/` باشد (به سبک OpenRouter)، پیشوند ارائه‌دهنده را نیز وارد کنید (مثال: `openrouter/moonshotai/kimi-k2`).
- اگر ارائه‌دهنده را حذف کنید، OpenClaw ابتدا ورودی را به‌عنوان نام مستعار، سپس به‌عنوان تطبیق یکتای ارائه‌دهنده پیکربندی‌شده برای همان شناسه دقیق مدل تفکیک می‌کند و فقط پس از آن با هشدار منسوخ‌شدن به ارائه‌دهنده پیش‌فرض پیکربندی‌شده بازمی‌گردد. اگر آن ارائه‌دهنده دیگر مدل پیش‌فرض پیکربندی‌شده را ارائه نکند، OpenClaw به‌جای نمایش یک پیش‌فرض کهنه از ارائه‌دهنده حذف‌شده، به اولین ارائه‌دهنده/مدل پیکربندی‌شده بازمی‌گردد.
- `models status` ممکن است در خروجی احراز هویت برای جای‌نگهدارهای غیرمحرمانه (برای مثال `OPENAI_API_KEY`، `secretref-managed`، `minimax-oauth`، `oauth:chutes`، `ollama-local`) به‌جای پوشاندن آن‌ها به‌عنوان اسرار، `marker(<value>)` را نشان دهد.

### تنظیم مدل پیش‌فرض / تصویر

```bash
openclaw models set <model-or-alias>
openclaw models set-image <model-or-alias>
```

`set`، `agents.defaults.model.primary` را می‌نویسد؛ `set-image`، `agents.defaults.imageModel.primary` را می‌نویسد. هر دو `provider/model` یا یک نام مستعار پیکربندی‌شده را می‌پذیرند. هنگامی که مدل تازه انتخاب‌شده به نصب Plugin زمان اجرای Codex/Copilot نیاز داشته باشد، `set` آن نصب‌ها را نیز تعمیر می‌کند؛ `set-image` چنین کاری نمی‌کند. هیچ‌کدام از دستورها `--agent` را نمی‌پذیرند؛ آن‌ها همیشه پیش‌فرض‌های عامل را می‌نویسند.

### اسکن

`models scan` کاتالوگ عمومی `:free` متعلق به OpenRouter را می‌خواند و نامزدها را برای استفاده به‌عنوان جایگزین رتبه‌بندی می‌کند. خود کاتالوگ عمومی است، بنابراین اسکن‌های صرفاً فراداده‌ای به کلید OpenRouter نیاز ندارند.

OpenClaw به‌طور پیش‌فرض تلاش می‌کند با فراخوانی‌های زنده مدل، پشتیبانی ابزار و تصویر را کاوش کند. اگر هیچ کلید OpenRouter پیکربندی نشده باشد، دستور به خروجی صرفاً فراداده‌ای بازمی‌گردد و توضیح می‌دهد که مدل‌های `:free` همچنان برای کاوش و استنتاج به `OPENROUTER_API_KEY` نیاز دارند.

گزینه‌ها:

- `--no-probe` (فقط فراداده؛ بدون جست‌وجوی پیکربندی/اسرار)
- `--min-params <b>`
- `--max-age-days <days>`
- `--provider <name>`
- `--max-candidates <n>`
- `--timeout <ms>` (مهلت زمانی درخواست کاتالوگ و هر کاوش)
- `--concurrency <n>`
- `--yes`
- `--no-input`
- `--set-default`
- `--set-image`
- `--json`

`--set-default` و `--set-image` به کاوش زنده نیاز دارند؛ نتایج اسکن صرفاً فراداده‌ای فقط اطلاع‌رسانی هستند و روی پیکربندی اعمال نمی‌شوند.

## نام‌های مستعار

```bash
openclaw models aliases list [--json] [--plain]
openclaw models aliases add <alias> <model-or-alias>
openclaw models aliases remove <alias>
```

نام‌های مستعار به‌ازای هر ورودی مدل در `agents.defaults.models.<key>.alias` ذخیره می‌شوند. `add` ابتدا `<model-or-alias>` را به یک کلید متعارف ارائه‌دهنده/مدل تفکیک می‌کند؛ بنابراین نام مستعارکردن یک نام مستعار، به‌جای ایجاد زنجیره، آن را دوباره هدف‌گذاری می‌کند.
افزودن نام مستعار، `agents.defaults.modelPolicy.allow` را تغییر نمی‌دهد یا لغو مدل را محدود نمی‌کند.

## جایگزین‌ها

```bash
openclaw models fallbacks list [--json] [--plain]
openclaw models fallbacks add <model-or-alias>
openclaw models fallbacks remove <model-or-alias>
openclaw models fallbacks clear
```

`agents.defaults.model.fallbacks` را مدیریت می‌کند. `openclaw models image-fallbacks list|add|remove|clear` فهرست موازی `agents.defaults.imageModel.fallbacks` را با همان ساختار زیردستور مدیریت می‌کند.

## پروفایل‌های احراز هویت

```bash
openclaw models auth add
openclaw models auth list [--provider <id>] [--json]
openclaw models auth login --provider <id>
openclaw models auth login --provider openai --profile-id openai:work
openclaw models auth login-github-copilot
openclaw models auth paste-api-key --provider <id>
openclaw models auth setup-token --provider <id>
openclaw models auth paste-token --provider <id>
openclaw models auth order get --provider <id>
openclaw models auth order set --provider <id> <profileIds...>
openclaw models auth order clear --provider <id>
```

`models auth add` راهنمای تعاملی احراز هویت است. بسته به ارائه‌دهنده‌ای که انتخاب می‌کنید، می‌تواند جریان احراز هویت ارائه‌دهنده (OAuth/کلید API) را آغاز کند یا شما را برای جای‌گذاری دستی توکن راهنمایی کند.

`models auth list` پروفایل‌های احراز هویت ذخیره‌شده برای عامل انتخاب‌شده را بدون نمایش توکن، کلید API یا اطلاعات محرمانه OAuth فهرست می‌کند. برای محدود کردن نتایج به یک ارائه‌دهنده، مانند `openai`، از `--provider <id>` و برای اسکریپت‌نویسی از `--json` استفاده کنید.

`models auth login` جریان احراز هویت Plugin ارائه‌دهنده (OAuth/کلید API) را اجرا می‌کند. برای مشاهده ارائه‌دهندگان نصب‌شده از `openclaw plugins list` استفاده کنید. `login` برای ارائه‌دهندگانی که هنگام ورود از پروفایل‌های نام‌گذاری‌شده پشتیبانی می‌کنند، `--profile-id <id>` را می‌پذیرد (از این گزینه برای جدا نگه‌داشتن چند ورود مربوط به یک ارائه‌دهنده استفاده کنید)، `--method <id>` برای انتخاب یک روش احراز هویت مشخص، `--device-code` به‌عنوان میان‌بری برای `--method device-code`، `--set-default` برای اعمال مدل پیش‌فرض پیشنهادی ارائه‌دهنده، و `--force` برای حذف اولیه پروفایل‌های موجود آن ارائه‌دهنده است (زمانی استفاده کنید که یک پروفایل OAuth ذخیره‌شده در حافظه نهان گیر کرده باشد یا بخواهید حساب را تغییر دهید).

`models auth login-github-copilot` میان‌بری برای `models auth login --provider github-copilot --method device` (جریان دستگاه GitHub) است؛ این فرمان `--yes` را برای بازنویسی یک پروفایل موجود بدون درخواست تأیید می‌پذیرد.

برای نوشتن نتایج احراز هویت در مخزن یک عامل پیکربندی‌شده مشخص، از `openclaw models auth --agent <id> <subcommand>` استفاده کنید. پرچم والد `--agent` توسط `add`، `list`، `login`، `paste-api-key`، `setup-token`، `paste-token`، `login-github-copilot` و `order get`/`set`/`clear` رعایت می‌شود.

برای مدل‌های OpenAI، مقدار پیش‌فرض `--provider openai` ورود با حساب ChatGPT/Codex است. تنها زمانی از `--method api-key` استفاده کنید که می‌خواهید یک پروفایل کلید API مربوط به OpenAI اضافه کنید؛ معمولاً به‌عنوان پشتیبان برای محدودیت‌های اشتراک Codex. برای مهاجرت وضعیت قدیمی و منسوخ احراز هویت/پروفایل با پیشوند OpenAI Codex به `openai`، فرمان `openclaw doctor --fix` را اجرا کنید.

نمونه‌ها:

```bash
openclaw models auth login --provider openai --set-default
openclaw models auth login --provider openai --method api-key
openclaw models auth paste-api-key --provider openai
openclaw models auth list --provider openai
```

نکته‌ها:

- `paste-api-key` کلیدهای API تولیدشده در جای دیگر را می‌پذیرد، مقدار کلید را درخواست می‌کند و آن را در شناسه پروفایل پیش‌فرض `<provider>:manual` می‌نویسد، مگر اینکه `--profile-id` را وارد کنید. در خودکارسازی، کلید را از طریق ورودی استاندارد ارسال کنید؛ برای نمونه `printf "%s\n" "$OPENAI_API_KEY" | openclaw models auth paste-api-key --provider openai`.
- `setup-token` و `paste-token` همچنان فرمان‌های عمومی توکن برای ارائه‌دهندگانی هستند که روش‌های احراز هویت مبتنی بر توکن ارائه می‌دهند.
- `setup-token` به یک TTY تعاملی نیاز دارد و روش احراز هویت توکنی ارائه‌دهنده را اجرا می‌کند (در صورت وجود، روش پیش‌فرض آن ارائه‌دهنده یعنی `setup-token`).
- `paste-token` به `--provider` نیاز دارد، به‌طور پیش‌فرض مقدار توکن را درخواست می‌کند و آن را در شناسه پروفایل پیش‌فرض `<provider>:manual` می‌نویسد، مگر اینکه `--profile-id` را وارد کنید. در خودکارسازی، به‌جای ارسال توکن به‌عنوان آرگومان، آن را از طریق ورودی استاندارد ارسال کنید تا اعتبارنامه‌های ارائه‌دهنده در تاریخچه پوسته یا فهرست فرایندها ظاهر نشوند.
- `paste-token --expires-in <duration>` زمان انقضای مطلق توکن را بر اساس مدتی نسبی مانند `365d` یا `12h` ذخیره می‌کند.
- برای `openai`، کلیدهای API مربوط به OpenAI و اطلاعات توکن ChatGPT/OAuth قالب‌های احراز هویت متفاوتی دارند. از `paste-api-key` برای کلیدهای API مربوط به `sk-...` در OpenAI و از `paste-token` فقط برای اطلاعات احراز هویت توکنی استفاده کنید.
- Anthropic: مسیرهای `setup-token`/`paste-token` برای احراز هویت `anthropic` در OpenClaw پشتیبانی می‌شوند، اما در صورت موجود بودن Claude CLI ‏(`claude -p`) روی میزبان، OpenClaw استفاده مجدد از آن را ترجیح می‌دهد.
- `auth order get/set/clear` بازنویسی ترتیب پروفایل‌های احراز هویت مختص هر عامل را برای یک ارائه‌دهنده مدیریت می‌کند که در `auth-state.json` ذخیره می‌شود (جدا از کلید پیکربندی `auth.order.<provider>`). `set` یک یا چند شناسه پروفایل را به‌ترتیب اولویت می‌پذیرد؛ `clear` به ترتیب پیکربندی/گردشی بازمی‌گردد.
